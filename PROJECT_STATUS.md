The 16,000 x 16,000 ATF JPEG exceeded Pillow's default hard pixel limit. A bounded JPEG draft decode produced its 480-pixel cached thumbnail on production without replacing application code. Local thumbnail generation now uses that bounded draft path for large JPEGs; this source change has not been deployed.
- The final backfill reported 37,722 scanned, 0 newly created, 31,620 cached, and 6,102 skipped. Seven explicitly failed originals lacked cache entries. Their thumbnails were generated and verified on production: four slightly truncated JPEGs decoded with Pillow's truncated-image mode, and three e621 vector SWFs were exported to still frames with an offline Flash frame exporter. All seven now have valid JPEG cache entries at no more than 480 pixels on either side. The original files and application code on production were not changed.
- Saved image posts use a locally generated, 480-pixel JPEG thumbnail. On November 5, the cache location was changed from `/data/thumbnails` to `/downloads/thumbnails`, which maps to the NAS download mount in the production stack. The NAS mount was verified as a CIFS mount from `nas.thelinclan.com`. The cache key includes the saved path, file size, and modification time. Posts without a saved image continue to use the source preview; unsupported local files fall back to it. The user deployed the earlier `/data/thumbnails` version and reported that thumbnail generation overloaded the Docker host's local disk. The new cache-location change is local source only and has not been deployed or tested on production. Python compilation, JavaScript syntax, Compose configuration, diff check, and a clean Docker build passed (local image `booru-downloader:nas-thumbnails`, `sha256:d2da3a6414231ccaf57f12aa1e640c474fb621738ff0b9214c1d4bc5e9528052`).

Thumbnail generation is restricted to originals under `/downloads/booru/`, with cache output under `/downloads/thumbnails/`; saved files outside the booru folder use the source preview. `backfill_thumbnails.py` is a manual, one-time backfill for older saved files; it runs four thumbnail jobs in parallel by default, with configurable concurrency and no artificial delay. It does not start with the service. New downloads in that folder generate their thumbnail after saving, with up to four concurrent image generations by default (`THUMBNAIL_WORKERS`). Both paths use the same deterministic cache key, so no database schema change is needed to link the cached copy to a post. Unsaved posts still use the source preview. These changes are local source only and have not been deployed or run on production; the database backfill and a live download have not been tested.

## Recorded failures and risks

- The database retains 233 jobs with `error` status. They are historical records, not 233 currently running tasks. The largest groups are Danbooru downloads (86, often no original URL), shima downloads (60, often no original URL), and Rule34.xxx downloads (60, checksum or size failures). Five Sankaku crawl jobs also retain HTTP 401 errors. Inspect a job before retrying it.
- Queue dispatcher `GET_LOCK` timeouts occurred in logs on November 3. The app currently uses one named dispatch lock with a 30-second wait. No such error appeared in the last 24 hours of logs checked for this snapshot, but the underlying contention risk remains.
- Some remote posts do not expose an original URL or return a file matching their stated checksum or size. A successful site connection does not guarantee access to every original file.

Reuse the current `/data` volume and downloads root if retaining live state.

## Deployment pointers

See `README.md` for Compose setup. Keep the MySQL password file, TLS CA, credentials directory, `/data` volume, and `/downloads` mount persistent. The production database is `booru`; the running container and this repository should not both start workers against it.
